# Project A — results at a glance

One page. Every number is generated by `make eval` from a database rebuilt out of `data/`, and is reproduced in
[`evals/REPORT.md`](../evals/REPORT.md) with a failure analysis. All data is synthetic; the customer is fictional.

**Live:** API https://app-production-4016.up.railway.app · portal https://portal-production-6ba2.up.railway.app

## What it does

A governed path from plant extract to published numbers: profile → map (AI proposes, owner confirms, versioned)
→ validate (deterministic rules, nothing dropped) → publish (refuses stale or drifted batches) → consumer views
compiled from one metric definition → reconciliation that explains each BI tool's gap. Plus a permission-filtered
knowledge layer and one exception-triage agent whose every action needs an owner.

## The three things worth two minutes of a reviewer's time

1. **The policy gate blocks a fix that is correct.** The agent proposes normalising `CUST-0004` to `C000004`,
   which is right. SOP-DQ-001-v2 permits automatic changes only to units and date formats, so the gate refuses
   it in code and it becomes a proposal for a person. Sixteen of sixteen adversarial fixes are blocked, and the
   allowlist cannot be widened from the config file.
2. **Coverage honesty, 17 / 17.** Cedar Falls sent no lot numbers before June 2026. Those exceptions must come
   back as "the source does not carry this field for this period" — not a fix, and not a compliance escalation.
   Every one does.
3. **The report includes what fails.** Two evaluations miss their targets and say why: the agent at 82%, where
   the pattern it gets wrong is the one whose expected label has no prior resolution behind it, and one retrieval
   miss on a long document that also causes an over-refusal.

## Engineering practice

- **33 decisions** in `docs/decisions.md`, each with alternatives, reason and evidence.
- **376 tests**, including a failure-case catalogue checked against the plan, and a policy-gate adversarial suite.
- **CI on every push**: lint, regenerate the synthetic data, run the tests against pgvector Postgres, run the
  deterministic evals strictly. Deploy to Railway only after green.
- **Nothing writes to a system of record automatically.** Mappings, exception resolutions, drift alerts, publish
  and agent applies all require an owner.
- **Secrets in environment only**; `.env.example` committed; no engagement-identifying terms in the repo, guarded
  by a test.

## Honest limits

- The agent is below its accuracy target, and the label it misses most is mine rather than a customer's.
- Retrieval still ranks near-duplicate plant profiles and prior resolutions above the document a couple of
  questions need.
- The data is synthetic from a fixed seed, and a real M3 adapter is an interface swap that has not been done.
- Project B (the command center that consumes this gold) is planned, not built.
