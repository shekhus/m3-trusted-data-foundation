### D-009 · 2026-09-15 · Migrations and database tests are Postgres-only; the app container migrates on start

- **Decision:** `db/migrate.py` applies numbered plain-SQL files from `db/migrations/` to Postgres and refuses any other backend. Each file runs in one transaction with its `public.schema_migrations` row (version, name, sha256 of the LF-normalised file); a session advisory lock serialises runners. It refuses an applied file whose checksum changed, an applied file missing from disk, and a new file numbered below the latest applied one. `0001` creates `bronze/silver/gold/ops`; `0002` creates the six ops tables named in CLAUDE.md with the plan §2.4 columns and constraints that encode the contracts (one confirmed mapping per source; one exception per batch × rule × row; a resolved exception needs who/when/what; `rule_id` matches `V###`). `bronze.raw_*`, `silver.*`, `gold.*` and the later ops tables (`tool_calls`, `runs`, `reconciliation`) arrive with their features. Database tests take a fresh throwaway database per test via the `pg_url` fixture and **skip** when Postgres is unreachable; `REQUIRE_POSTGRES=1` turns the skip into a failure (for CI). The Dockerfile runs `scripts/migrate.py` before uvicorn, so `docker compose up` alone yields the schemas (week-1 definition of done).
- **Alternatives:** one SQLite file per schema via `ATTACH` (tests run without Docker); Alembic; migrate only via `make migrate`.
- **Reason:** production is Postgres and the schema will use Postgres features (`jsonb`, partial unique indexes, regex checks, `gen_random_uuid`), so SQLite tests would test a different database. Alembic adds autogenerate machinery CLAUDE.md rules out (plain SQL, no ORM schema). Migrating on start is safe under the advisory lock. The SQLite fallback in `app/config.py` (D-003) stays for the API's `/healthz` only and is not migrated.
- **Verified:** 13 migration tests green against Postgres 18.6 in Compose, including a deliberately broken migration leaving no table and no record (this caught a real bug: SQLAlchemy did not track the transaction opened by the raw psycopg call, so the rollback was a no-op — fixed by beginning the transaction explicitly). From `docker compose down -v`, `docker compose up` applies 0001–0002 and a restart reports "database is up to date". With Postgres down the 7 database tests skip in ~6 s.

### D-010 · 2026-09-15 · Profiler infers from files and masters only; findings are committed and checked against the answer key

- **Decision:** `pipeline/profile.py` profiles every `data/sources/<source>/*.csv` (read as raw strings, nothing coerced) plus `data/master/`, and returns Pydantic `SourceProfile`s. Per column: dtype, blank %, distinct %, whitespace %, negatives, min/max, top value shapes (digit→9, letter→A), date format (ISO; slash dates resolved to US/DMY only when a part exceeds 12, otherwise `slash_ambiguous`; Excel serials by range 2000–2050), master match after trimming, and lb/kg from **both** header tokens and magnitude — median of `weight / (qty × item avg_lb_per_case)`, ≈1.0 lb, ≈0.4536 kg; disagreement is reported as a conflict, not resolved. Per source: header variants across files, the 1–2 column key with the fewest duplicates, exact duplicate rows, and plain-language findings. `make profile` writes `docs/findings.md` + `docs/findings.json` (deterministic; committed; a test fails when they are stale).
- **Alternatives:** read `ground_truth/mappings.json` for formats (cheating — the mapping eval would be circular); header-only unit inference (misses PLT-01/PLT-03, whose weight headers name no unit); prefer single-column keys (picks `Lot`, near-unique, over `(Order, Line)` at PLT-03); digit-normalised customer matching (line numbers and quantities also "match" bare customer numbers — left to the week-2 mapper).
- **Reason:** the profile is the mapper's input, so it must stand on the files alone; tests then score it against the answer key. **Verified against ground truth (tests/test_profile.py):** date format and weight unit for every mapped column at all three plants (magnitude alone agrees with the key); only the answer-key weight columns get a unit; both drift events show as header changes in the right month; trailing whitespace only on PLT-03 items; key duplicates = seeded V008 per plant (27/33/20); negative quantities = seeded V007 (16/14/5); the rare `LB` UOM shape = seeded V009 (28/13/14).
- **Finding:** `data/DATASET.md` and plan §1.3 say PLT-03 has ~0.5% ambient duplicate rows, but `synth/config.py` sets `ambient_dup_rate` to 0 for every plant; the profiler sees only the 20 seeded V008 duplicates at PLT-03. Generator left unchanged (the answer key is locked); the docs claim is wrong, not the data.

### D-011 · 2026-09-15 · Metric dictionary as versioned YAML compiled through a whitelisted expression language

- **Decision:** one file per metric version, `metrics/<metric>.v<version>.yaml`, validated by a Pydantic model (`extra="forbid"`; owner, changed_by, effective_from, status `current|legacy`, at most one current version per metric). Expressions follow the plan's example syntax (`issue_date <= confirmed_delivery_date`, `a if flag else b`, `sum(otif) / count(*)`). `metrics/compiler.py` parses them with Python's `ast` and renders SQL through a whitelist (comparisons, `in`, and/or/not, arithmetic, if/else, literals, names, and sum/avg/count/min/max in aggregations only); anything else is a `CompileError`. Each version compiles to one row-level view `gold.<metric>_v<version>_lines` holding the key, `metric_date`, dimensions and every input/rule as a boolean (missing input → FALSE); `aggregate_sql()` groups it by `day`/`month` and declared dimensions, with division as `x::double precision / NULLIF(y, 0)`. `apply()` checks every referenced name is a real column of the source table before creating views, so an unknown name (including a SQL function name) cannot reach Postgres. Compiled SQL is committed under `metrics/compiled/` with a staleness test. Shipped: `otif.v3` (governed), `otif.v2` (legacy, count basis for all items), `fill_rate.v1`. Migration `0003` adds `gold.fact_delivery` with **no** precomputed flags, so the YAML stays the only definition; `product_group` and `catch_weight_flag` are denormalised onto the fact because rules read them.
- **Alternatives:** Jinja SQL templates (definitions become SQL again, and injection-prone); dbt/MetricFlow (a framework for three metrics); `eval` of the expressions (unsafe); one YAML per metric with a version list (the legacy view needs the old definition as a first-class file).
- **Reason:** CLAUDE.md principle 5 — consumer views are compiled, never hand-written — needs a compiler that owners can read and reviewers can trust. **Verified (tests/test_metrics_compiler.py, Postgres 18):** loading the generator's 51,571-row gold fact, `otif.v3` by day × plant equals `data/metrics/daily_otif_plant` (lines exact, rates within 1e-9); `fill_rate.v1` by day equals `daily_otif_total`; by month, `otif.v3` equals `reconciliation.json` governed OTIF and `otif.v2` equals the legacy BI tool's OTIF for all 18 months (5 dp). Tool 2's differences (requested-date basis, 2% case tolerance, CONS excluded) are not a dictionary version — they belong to reconciliation attribution in week 4.

### D-013 · 2026-09-15 · Mappings bind to an exact header; heuristic mapper scored on answer-key and unseen headers

- **Decision:** a mapping is for one source **header** (ordered column list, `header_hash` = sha256 of it), not a whole source. Migration `0004` adds `header`/`header_hash`/`rejected_by`/`rejected_at` and moves the one-confirmed rule to `(source, header_hash)`. `pipeline/canonical.py` defines the 15-column canonical order line (names only; M3 physical names still to confirm with an SME) and the transform vocabulary. `pipeline/mapper/contract.py` is the single contract for heuristic, LLM, API and portal: every header column exactly once, known canonical names and transforms only, no canonical column twice. `pipeline/mapper/heuristic.py` scores pairs as 0.55 × name (concept Dice over an ERP-abbreviation vocabulary with run-together splitting) + 0.45 × profile evidence (dtype, unit, master match, distinctness; hard mismatches excluded), assigns greedily one-to-one, and derives transforms from the profile (date parser per detected format, `kg_to_lb`, `normalize_customer_no`, `trim`). API (`app/routers/mappings.py`, `X-API-Key` roles in `app/auth.py`): analyst/owner propose (one version per header variant, repeat proposals deduplicated) or submit a human-corrected mapping; **only owner** confirms or rejects; confirm is refused (422) while required canonical columns are unmapped and supersedes the previous confirmed mapping for that header; deciding a non-proposed version is 409. Compose mounts `./data` read-only into the app. Profiles are cached by file path/size/mtime.
- **Alternatives:** one mapping per source with optional columns (hides drift: PLT-02's `cust_no` and `customer_number` would both "map", so a rename could never block publish); Hungarian assignment (greedy already optimal on every case; revisit if it is not); fuzzy string distance instead of concepts (`ORDERNUM` vs `order_no` needs splitting, not edit distance).
- **Reason:** drift detection (week 4) needs "this header has no confirmed mapping" to be a fact in the database. **Measured (`make eval-mapping`):** answer-key headers 74/74 columns top-1 and 35/35 transforms across 5 headers — optimistic, because the vocabulary was written looking at these sources. The unseen-header case (`evals/cases/mapping_unseen_headers.yaml`, PLT-01 data under ERP-style names) scores **9/14 (64.3%)**, missing SalesDocument, ItemPosition, SoldToParty, ShippingPoint, CreatedOn — so required columns stay unmapped and confirm is blocked until a person or the LLM fills them. A test fails if that case reaches 100%, to catch the vocabulary being tuned to the eval. Failure cases (plan §2.6) in `tests/failure_cases/`: analyst and viewer get 403 on confirm/reject; an LLM-style answer naming a column not in the header is rejected by the contract.

### D-014 · 2026-09-15 · LLM mapper: one structured-output call behind llm/client.py, retry once, heuristic fallback

- **Decision:** `llm/client.py` is the only LLM entry point. `AnthropicBackend` sends one `messages.create` with `output_config.format` = a JSON schema (enums pin header column names, canonical names and transforms); the answer is parsed by the caller's Pydantic contract, not by the SDK, so fake and real backends share one path and a bad answer is visible as `invalid_output`. Every attempt is a row in `ops.llm_calls` (provider, model, sha256 prompt hash, tokens, latency, cost from `LLM_PRICE_*`, outcome, error). Refusal and `max_tokens` stops count as provider errors. `pipeline/mapper/llm.py` always runs the heuristic first, sends the canonical schema, transform meanings, column profiles (statistics plus at most 3 example values per column, never raw rows), the heuristic proposal and owner-confirmed mappings of *other* sources; an invalid answer is retried once with the validation error appended; a second invalid answer or any provider error returns the heuristic proposal with `needs_review`. The propose endpoint stores the heuristic proposal and, when the model answered validly, the LLM proposal as a separate version — the owner compares and confirms one. `make eval-mapping --llm` scores only headers the model actually answered and lists fallbacks separately, and passes no confirmed examples (the unseen-header case is PLT-01's data; examples would leak the answer). Model `claude-sonnet-5` ($2 / $10 per MTok, verified against the Claude API reference 2026-09-15), per plan §1.1.
- **Alternatives:** `client.messages.parse` with the Pydantic model (SDK-side parsing hides invalid outputs from the call log and ties tests to the SDK); tool use for JSON (structured outputs are the direct fit); letting the LLM proposal replace the heuristic one (loses the baseline the owner and the eval compare against); an agent loop (fails the justification test: the step count is fixed).
- **Reason:** principle 1 (AI proposes, never applies) and the convention that LLM output is contract-parsed, logged, retried at most once and falls back to the heuristic. **Verified:** 10 tests with a scripted backend cover ok, invalid-then-valid retry, hallucinated column twice → flagged heuristic fallback with exactly two calls, provider error → fallback with no retry, prompt contents, `ops.llm_calls` rows in Postgres, and the API storing heuristic + LLM versions. A live run on 2026-09-15 reached the API with the project key and logged 6 `error` calls: the account has no credit (`req_011Cf4iTqm38h4K3sYRTyQpF`). **LLM mapping accuracy is therefore not measured yet**; `tests/test_llm_mapper.py::test_live_provider_returns_a_contract_valid_mapping` runs with `RUN_LIVE_LLM=1` once credit exists.

### D-015 · 2026-09-15 · Bronze as generic JSON rows; silver derived from bronze through the header's confirmed mapping

- **Decision:** migration `0005` adds `bronze.raw_order_lines(batch_id, source_row, record jsonb)` — every source row as received, text values keyed by that file's header — and `silver.order_lines` with the 15 canonical columns typed, plus `source`, `mapping_version_id`, and `parse_errors jsonb` (canonical column → raw value). Silver rows reference their bronze row. `pipeline/ingest.py` makes one batch per file with idempotency key `file:<source>:<name>:<sha256>`: a replay returns the original batch and writes nothing. Bronze is always loaded; silver is built only when the file's exact header has a confirmed mapping, otherwise the batch is `blocked` naming the header, and a later run after confirmation maps the stored bronze rows (resume, same batch id). `pipeline/transforms.py` applies the mapping's transforms then parses to type; a non-blank value that fails becomes NULL with its raw value in `parse_errors`; blanks stay NULL without error (V001's job, week 3). ### D-017 · 2026-09-15 · Groq (openai/gpt-oss-120b, strict JSON schema) as the configured provider; LLM lift measured

- **Decision:** add `GroqBackend` to `llm/client.py` next to `AnthropicBackend`; `LLM_PROVIDER=groq` selects it. It calls Groq's OpenAI-compatible chat completions with `httpx` (already a dependency; no extra SDK pinned) and `response_format = {type: json_schema, json_schema: {name, strict: true, schema}}` — constrained decoding, supported on `openai/gpt-oss-120b` per Groq's structured-outputs docs (read 2026-09-15). Non-2xx and any `finish_reason` other than `stop` are provider errors. A 429 with `retry-after` ≤ 30 s is waited out once (transport, not a second answer); longer limits fail fast. The local `.env` uses `LLM_MODEL=openai/gpt-oss-120b`, `LLM_PRICE_IN/OUT_PER_MTOK=0.15/0.60` (Groq models page, 2026-09-15); `GROQ_API_KEY` is in `.env.example` and passed through Compose. The Anthropic backend stays and is selectable. `scripts/eval_mapping.py` gains `--pace` (seconds between LLM headers, for tokens-per-minute limits) and `--case`.
- **Alternatives:** the `groq` SDK (a new unverified dependency for one POST); JSON mode without a schema (no guarantee of shape); `openai/gpt-oss-20b` (cheaper; not measured); waiting indefinitely on 429 (hides a daily cap as a hang).
- **Reason:** the Anthropic account has no credit (D-014), and the plan requires the LLM-assisted mapping accuracy to be measured, not assumed. **Measured 2026-09-15 (`--llm --pace 60`, no confirmed examples):** answer-key headers 5/5, 74/74 columns, 35/35 transforms — equal to the heuristic. **Unseen ERP-style headers: 14/14 columns and 7/7 transforms in 3 of 3 runs, against the heuristic's 9/14 and 6/7** — the LLM mapped SalesDocument, ItemPosition, SoldToParty, ShippingPoint and CreatedOn that the heuristic left unmapped. One of the 13 successful attempts first returned a contract-invalid answer and was recovered by the single retry. Groq spend for all runs ≈ $0.02 (`ops.llm_calls`). Caveats: one unseen header of 14 columns is a small sample, and the free tier's 8,000 tokens/minute makes an unpaced run fall back (the eval reports those as fallbacks, never as accuracy). The plan target (top-1 ≥ 90% LLM-assisted) is met on both cases.

### D-018 · 2026-09-15 · Rules V001–V011 as deterministic DataFrame checks over silver; exceptions keyed by source row; V006 ceiling corrected from the data

- **Decision:** `rules/` holds one class per rule (`id`, `name`, `severity`, `owner`, `message`, `suggested_fix`, `check(df, ctx) -> Violations` with per-row evidence), registered in `rules/__init__.py`. `pipeline/validate.py` runs every rule on a batch's silver rows after silver is built, inserts `ops.exceptions` idempotently (migration `0006`: identity is `(batch, rule, source_row)` with a foreign key to the bronze row — `(order_no, line_no)` is not unique in a batch, which is V008's finding — plus `source` and `details` evidence), resolves open exceptions that no longer apply on re-validation as `system:revalidation` (never deletes), and records `rows_validated` and `rules_run` on the batch (status `validated`).
