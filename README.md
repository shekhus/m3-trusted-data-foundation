# M3 Trusted Data Foundation

**All data in this repository is synthetic, and the customer — Prairie Bend Foods — is fictional.** Tables are
modelled on Infor M3 order, delivery, inventory and production structures; field-level mapping to M3 physical
columns is to be confirmed with an M3 SME.

> Two BI tools, one truth: AI proposes the mappings, code validates every record, people confirm, and drift is
> caught before the report breaks.

## 1. Who is the customer?

Prairie Bend Foods (fictional): a multi-plant North American protein processor, about 1,200 people, three
plants (Cedar Falls, Hastings, Sheldon), running Infor M3. Its users are two supply-chain analysts, a BI
developer, three plant operations leads, and a VP Supply Chain who reads the reports.

Protein processing makes the data hard in specific ways:

- **Catch weight.** A case of primals is sold by actual weight, not a fixed weight per case. Counting cases and
  weighing them give different answers to "did we ship it in full?".
- **Shelf life and lots.** A lot shipped after its expiry date is a compliance finding, not a data error.
- **Multi-plant reality.** Each plant exports what its own systems produce: different column names, date
  formats, units and customer-number styles for the same business fact.

## 2. What was broken?

M3 extracts fed two BI tools. The legacy report suite carried hand-maintained SQL per report; the newer
dashboard tool rebuilt the metrics independently. The result:

- **The two tools disagreed** about on-time-in-full for the same week, and nobody could say which was right.
- **Refreshes broke silently** when a plant changed an extract: a renamed column produced a blank dashboard on
  Monday morning.
- **Bad rows skewed totals**: missing weights, duplicate lines, weights recorded in kilograms where the master
  says pounds.
- **About a third of BI tickets** were definition disputes rather than report bugs, and an analyst reconciled
  by hand in a spreadsheet.

## 3. What did you build?

A governed path from plant extract to published gold, where every step is inspectable and the consequential
ones need a person. Files are profiled, mapped onto a canonical schema (an LLM proposes, an owner confirms,
every mapping is versioned), validated by deterministic rules that never drop a row, and published to gold only
when the batch is clean, current and undrifted. Metrics are defined once in YAML and compiled into the consumer
views, so two views cannot disagree by accident, and a nightly reconciliation explains each BI tool's gap by
named cause. A retrieval layer answers questions from the company's own SOPs and memos with the asker's
permissions applied before the model call, and one agent — the only agentic component here — investigates an
exception with tools and proposes a classification that a policy gate in code, then an owner, must approve.

```
sources/{synthetic,m3_ion} → POST /ingest/{source} → profile → map → validate → publish
bronze.raw_*  →  silver.*  →  gold.*  →  consumer views (2 current + 1 legacy) → ops.reconciliation
ops.{mapping_versions, exceptions, lineage, batches, fingerprints, llm_calls, tool_calls, agent_runs}
retrieval.{chunks, embeddings}  →  /kb/ask (access-filtered, refuses when unsupported)
Portal: upload → findings → confirm mapping → batches → exceptions → reconciliation → knowledge → ops
```

## 4. How does it work? One record

A line for order `SO0001149`, item `IT97066`, arrives in `plt01_orderlines_2025-04.csv`.

1. **Profile.** The file's columns are typed and fingerprinted: `iss_dt` is an ISO date, `ord_wt` looks like
   pounds, `cust_no` matches the customer master.
2. **Map.** The header's shape has a confirmed mapping (`itm_no → item_no`, `ord_wt → ordered_weight_lb`), so
   the row loads into `bronze.raw_order_lines` as JSON and into `silver.order_lines` typed. An unknown header
   shape stops here: the batch is *blocked*, never guessed.
3. **Validate.** Twelve rules run on every row. `IT97066` is not in the item master, so V005 raises a blocking
   exception with the reason, a suggested fix and an owner (`master_data:items`). **The row is not dropped.**
4. **Triage (optional).** The agent investigates: a master lookup finds no match even after normalisation, and
   prior resolutions show the `IT9xxxx` pattern was "never created in the master". It classifies
   `needs_master_data`, cites its evidence, and stops for an owner.
5. **Publish.** Gold takes the batch's eligible rows. This row is held back while its exception is open, and
   the hold is counted by reason rather than hidden.
6. **Report.** OTIF and fill rate come from compiled consumer views. The row reappears in gold the moment master
   data is created and the batch is re-validated and published.

Meanwhile the same file's shape is remembered. When Cedar Falls adds `lot_no` in June 2026, the fingerprint
changes, an alert names the affected gold column and views, and publish refuses that shape until an owner
confirms the new mapping.

## 5. How did you evaluate it?

Everything below is from [`evals/REPORT.md`](evals/REPORT.md), generated by `make eval` on a database rebuilt
from `data/`. Model-dependent sections are read from their latest saved run and dated there.

| Measure | Target | Result |
|---|---|---|
| Validation coverage | 100% (hard gate) | **51,651 / 51,651 rows × 12 rules** |
| Exception recall / precision | ≥ 95% / ≥ 95% | **100% / 99.6%** |
| Drift detection | 2/2 detected and named | **2/2, 0 false alerts** |
| Consumer views agree | delta 0.00 every period | **114 / 114 green** |
| BI tool gap explained | causes and sizes match the key | **both tools pass** |
| Idempotency | replay 3× changes nothing | **unchanged** |
| Mapping (LLM-assisted) | top-1 ≥ 90% | **100%** known headers, **100%** unseen headers (heuristic: 100% / 64%) |
| Retrieval | 0 leaks; lift measured vs TF-IDF | **0 leaks** (4 unfiltered); recall **74% → 87%** |
| Grounded answers | 0 leaks | **51/53 good, 0 leaks** |
| Exception agent | ≥ 85%, no rule < 70% | **82% — target missed**; coverage hard gate **17/17** |
| Change absorption | report honestly | **1 dictionary file + 1 rule; 0 report SQL edited; ~17 min** |

**What surprised me.**

- **The similarity threshold is not a refusal mechanism.** The weakest *answerable* question scores below every
  unanswerable one, so any threshold that catches the unanswerable ones also refuses real questions. An explicit
  instruction plus a citation contract does that work.
- **Embeddings are not a free win.** They lift retrieval from 74% to 85%, but *lose* a long-document question
  that TF-IDF finds. The baseline is kept and reported for exactly that reason.
- **The agent's worst rule is where my own answer key is weakest.** It answers "needs master data" for a blank
  customer number where the case file says "source defect" — a label with no prior resolution behind it. It is
  reported as a miss rather than relabelled after the fact.
- **The policy gate rejecting a correct fix is the most useful test in the repo.** `CUST-0004 → C000004` is
  right, and the SOP still forbids applying it automatically.

## 6. What would you change before production?

- **Scale:** Delta or Databricks for volumes beyond a single Postgres; partitioned bronze retention rather than
  keeping every raw row forever.
- **A real M3 adapter** (ION API or the data lake) behind the existing `SourceAdapter` interface, with an M3 SME
  confirming physical field names.
- **SSO and per-user identity** instead of role API keys, and audit rows keyed to people.
- **Data contracts with source owners**, so a plant changing an extract is a negotiated version, not a surprise
  fingerprint.
- **Alert routing** (email, Slack, ticketing) from the ops views, rather than a tab someone has to open.
- **A reranker for near-duplicates** and document-versus-resolution balance in retrieval: the open C8 and C10
  misses are both ranking problems.
- **Human-labelled outcomes for the agent**, replacing my own expected labels where no prior resolution exists.

## Quickstart

Requires Python 3.12, and Docker for the full stack.

```
uv venv --python 3.12
uv pip install -r pyproject.toml --extra dev
make synth          # generate data/ + ground truth (deterministic, ~30s)
docker compose up   # Postgres + API (8000) + portal (8501)
```

Copy `.env.example` to `.env` for local settings. Without `LLM_PROVIDER`/`EMBEDDING_PROVIDER` the mapper falls
back to the heuristic and retrieval stays lexical; everything else works.

| Command | What it does |
|---|---|
| `make test` / `make lint` | pytest; ruff + mypy |
| `make eval` | full evaluation → `evals/results/<date>.json` + `evals/REPORT.md` |
| `make index` | chunk the knowledge base and embed what changed |
| `make ingest SRC=plt01` | ingest one source with a fresh idempotency key |
| `make reconcile` | consumer-view reconciliation and BI-tool attribution |
| `make eval-agent ARGS=--build` | score the A13 agent on a three-plant evaluation database |

More scripts: [`scripts/README.md`](scripts/README.md).
