## What this project is

A **trusted data foundation** for supply-chain reporting at a fictional multi-plant protein processor ("Prairie Bend Foods") running Infor M3. It ingests messy, plant-specific extracts, proposes field mappings with AI, validates every record with deterministic rules, holds bad rows in an exception queue, detects schema drift before reports break, and publishes governed gold tables that two independent consumer views reconcile against.

Portfolio project. All data is **synthetic**, generated by `synth/`. The customer is fictional. Never introduce real company names, real metrics, or client details into this repo.

Governing design document: `docs/plan.md` (Project A section). Discovery brief: `docs/discovery_brief.md`.

## Non-negotiable principles (from the FDE playbook)

1. **AI proposes, code validates, people confirm.** The LLM may suggest a mapping. It may never apply one, rewrite a value, or drop a row.
2. **Validation is deterministic and lives in `rules/`.** Every rule has an id (V001…), a severity, a message, and a suggested fix. No rule logic in prompts.
3. **Nothing is silently dropped or changed.** A row that fails a blocking rule goes to `ops.exceptions` with a reason and an owner. Auto-fixes (e.g. kg→lb) are logged with the original value.
4. **Every mapping is versioned** in `ops.mapping_versions`. Every gold column has lineage back to a source column in `ops.lineage`.
5. **One metric definition.** `metrics/*.yaml` is the only place a metric is defined. Consumer views are compiled from it, never hand-written.
6. **Idempotent ingest.** Same `Idempotency-Key` → same result, zero duplicate rows.
7. **Permissions are server-side.** Only `owner` role confirms mappings or resolves exceptions.
8. **Smallest abstraction that fits.** The ingest pipeline is fixed: profile → map → validate → publish. Plain Python. The ONLY agentic component in this repo is the exception resolution agent (A13), and it qualifies under the justification test below.
9. **Retrieval is permission-filtered before the model call**, never after generation. Over-restriction is a failure too: an authorised asker must get the answer.
10. **If the answer is not in the retrieved context, refuse.** Top-k always returns something. A similarity floor alone is not enough — the prompt must say so explicitly.

## The justification test (agentic components)

A component may become agentic ONLY if **the number of steps is not knowable in advance**. If you can draw the flowchart, write the flowchart.

| Component | Agentic? | Reason |
|---|---|---|
| Mapping proposer | **No** — one LLM call | Profile in, mapping out. Fixed shape. |
| Validation rules | **No** — no LLM at all | Deterministic. A rule that "usually" fires is not a rule. |
| Publish / reconcile | **No** | Fixed sequence. |
| **Exception agent (A13)** | **Yes** | The next tool depends on what the last one returned. Step count varies per exception. |

Keeping the mapper deliberately non-agentic is a deliberate design position, not an oversight. Do not "upgrade" it. If you believe another component needs a loop, write the reason in `docs/decisions.md` and stop.

## Agentic conventions (A13 only)

- Graph: `triage → investigate (tool loop, max 6 iterations) → classify → policy_gate → [interrupt_before: apply] → apply → record`.
- **Max 6 tool iterations**, then classify with whatever evidence exists. An agent that cannot conclude must say so, not loop.
- Outcomes are exactly four: `auto_fixable`, `needs_master_data`, `source_defect`, `escalate`. No fifth outcome, no "unsure" — low confidence is a field, not an outcome.
- **The auto-fix allowlist lives in `policy/autofix.yaml`, sourced from SOP-DQ-001-v2**: unit-of-measure normalisation and date-format normalisation only, both retaining the original value. Customer number, item number, quantity, and weight may NEVER be auto-fixed. The policy gate enforces this in code. An agent proposing a *correct* customer-number fix as an auto-fix is still rejected — it becomes a proposal for a human.
- Every classification carries `evidence_refs` (resolution ids, doc ids, or row keys). A classification with none fails the Pydantic contract.
- `interrupt_before=["apply"]` with the Postgres checkpointer. Nothing changes without an `owner` approving.
- Never bypass the interrupt "just for a test" — write a test that resumes the graph.

## Retrieval conventions

- Chunk at markdown section level. **Never split a table from its header row.**
- Every chunk carries `doc_id`, `version`, `status`, `access_level`, `plant`, `effective_date` from the document frontmatter.
- `status != current` is excluded by default. A document declaring precedence over another wins on the overlap. Historical questions may opt back in explicitly.
- Hybrid retrieval (embeddings + BM25, reciprocal rank fusion). **Keep the TF-IDF baseline and report it alongside** — the embedding lift must be measured, not assumed. Reporting a zero lift honestly is correct behaviour.
- Score retrieval **per challenge** (C1–C10), never as a single aggregate. An aggregate hides which failure mode is active.
- Permission leakage is reported as an **absolute count**, not a rate. One leak is a failure.

## Coding conventions

- Python 3.12, type hints everywhere, Pydantic v2 models for every API and LLM contract.
- SQL migrations are plain, numbered `.sql` files. No ORM-generated schema.
- Rules: `class V003InvoicedWeightTolerance(Rule)` with `id`, `severity`, `applies_to`, `check(df) -> Violations`. Register in `rules/__init__.py`. Add a test per rule with a seeded fault.
- LLM calls go through `llm/client.py` only. Every call is logged to `ops.llm_calls` (model, prompt hash, tokens, latency, cost, outcome).
- LLM outputs are parsed with a Pydantic contract. On failure: log, fall back to heuristic, flag for review. Never retry more than once.
- Secrets in env only. `.env.example` lists every variable. Nothing sensitive in git history.
- Tests: unit tests per module; integration test per pipeline stage; failure-case tests under `tests/failure_cases/`.
- Commit messages state the decision: `feat(drift): block publish on fingerprint change — reports named via lineage`.

## Things not to do

- Do not add a workflow/orchestration framework to the ingest pipeline. A13 is the only exception.
- Do not let the agent write to gold, silver, or any master. It proposes; the approved apply step writes to `ops.exceptions` only.
- Do not widen the auto-fix allowlist from code or from a prompt.
- Do not claim an embedding lift you have not measured against the TF-IDF baseline.
- Do not let a document above the asker's access level reach the model, even to be filtered out afterwards.
- Do not let the LLM see raw rows beyond a 20-row sample per column group for mapping.
- Do not hand-write consumer-view SQL; compile it from `metrics/*.yaml`.
- Do not invent M3 physical field names. Use canonical names; note "confirm with M3 SME" where a mapping to M3 is implied.
- Do not add real company names, client metrics, or anything from a real engagement.
- Do not pin package versions you have not verified against current docs.
- Do not delete or rewrite `ground_truth/` — the evals depend on it.
